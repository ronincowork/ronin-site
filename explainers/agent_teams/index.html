Agent teams

A role is who your agent is. A task is what it is doing now.

In Ronin, a session is launched into a family role it keeps for its whole life, and moves between session tasks as the work changes. One agent, one durable identity, many kinds of work — and several sessions working side by side make a team.

01

Every session is launched on three coordinates

When Ronin starts an agent session, three things describe it: a project root, a family role, and a session task. The project root is always required — a session has to be born somewhere. The role and the task are optional; a session can run with either or both left blank.

project root Where it works — the directory the session is born into. Required.
family role Who it is — chosen at launch, fixed for the life of the session.
session task What it is doing right now — changes as the work moves.
02

The family role is the durable hat

A role is the professional identity a session keeps: Developer, Assistant, Head Coach. It carries its own briefing — the reading that tells the agent how someone in that seat behaves — and its own launch defaults, so every session in that role starts set up the right way.

A role is fixed at launch. A Developer session never becomes a Personal Assistant halfway through; if you need a different hat, you start a different session. That stability is what makes a role worth briefing deeply.

03

Session tasks move with the work

A task is what the session is doing at this moment: planning, building, debugging, reviewing. When the work changes, the task changes — the session itself can switch it, or you can from the session's tile. A committed task change hands the agent that task's own briefing, so it knows how the new kind of work is done here.

The current task is also the mark you see next to the session in the Roster — a glance tells you what each agent is doing right now, not just what it was hired as.

04

Settings cascade from role to task

Both a role and a task can carry launch settings — which model to prefer, what permissions to start with, how the session opens. They layer in a fixed order: the system default, then the role, then the task, then whatever you choose explicitly for this one launch. Each layer overrides only what it actually states; everything else is inherited.

05

Tasks are shared; roles organize them

A task is not owned by a role. The same task can sit in several roles' families — planning is planning whether a Developer or a House Manager is doing it. The role decides which tasks belong to its family; moving a task between roles changes the family, not the task.

That is why the use cases below are teams rather than org charts: a team is a role plus the tasks it works through, and several sessions running side by side — each with its own role and its own current task — cover a whole workload together.

Common questions

Family roles and session tasks

Can a session change its role?

No. The role is chosen at launch and fixed for the session's life. The task is the part that moves. If the role itself is wrong, start a new session in the right one.

Do I have to pick a role or a task?

No. Both are optional. A blank role or task simply means no extra briefing for that axis — the session runs on what you type.

Is a role a different AI model?

No. The same agent programs — Claude Code, Codex, Gemini, and the others — run in every role. A role is briefing and defaults around the agent, not a different brain. A role or task can prefer a model, but your agent and your account stay your own.

Can I make my own roles and tasks?

Yes — roles and tasks are definitions you can add to your Ronin and share, and you do it by telling your agent what you want. The fitness and home management teams are exactly that: roles an owner defines for their own use. See Make Ronin your own.
