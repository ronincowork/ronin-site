Explainers / Checkouts and Worktrees

How should Agents work in this repository?

Two ways to work. Choose one per repository.

A repository under Ronin is either a checkout, where everyone works in one folder, on whatever branches they like but only one at a time, or it uses Ronin Worktrees, where each Agent gets a private folder and branch and finished work is patched back together through a review step. The choice is made once per repository, both are first-class, and one Agent can hold both at the same time in different repositories.

The two models

Here are the two options, and this is what each looks like.

Use the checkout

One folder, one or more branches, everyone in it.

  • Work happens in the checkout itself. Commit on the branch as you go; that is the line moving.
  • Ronin stays out. No hand-in, no lead, no records. Ordinary Git, yours to run how you like.
  • Collisions are yours to avoid. A folder can have only one branch checked out at a time. Three Agents on three branches in one folder still collide: each switch swaps the files out from under the others. Branches alone do not isolate anyone.

Fits a workspace: notes, plans, a scratch repository, anything without a release.

Use Ronin Worktrees

A private folder per Agent, patched back together through review.

  • Work happens in a private folder on a private branch, cut from the local working line.
  • Ronin runs the loop. Commit, hand in to the team's line, the Team lead reviews and promotes. Every step leaves a receipt.
  • Collisions cannot happen. A worktree is a branch with its own folder, so each Agent's files are its own. Many Agents edit at once; nobody's switch or half-finished edit reaches anyone else until the work is accepted.

Fits a product: a codebase with a release, tests, and several Agents at once.

The line between the two is the folder, not the branch. Git lets you make as many branches as you like, but one checkout can only show one of them, so "just make your own branch" is still everyone sharing one set of files. A worktree gives a branch its own folder. That is what lets several Agents work at once, and it is why the worktrees model needs the hand-in and the lead's look: the pieces were made apart and have to be patched back together on purpose. The checkout model puts nothing there, because in a workspace nothing needs to be there.

Inside the worktrees model

Two branches are the truth. Everything else is on loan.

A repository declares its arrangement once, in a small file at its root: which branch is the working line, which is the stable line, and whether Agents get worktrees. From then on every tool reads that file, and nothing is decided by whichever branch happens to be checked out. In the worktrees model that file names two branches that matter and, by omission, everything that does not.

  • local · working lineAccepted work

    Usually dev. Nobody edits it in place. Work reaches it by promotion, and every new worktree is cut from it. This is the branch that means "what we have agreed on".

  • remote · stable lineReleased work

    Usually master or main on GitHub. It moves only by a pull request from the working line, which you review and merge yourself. Between releases it is your final gate.

  • everything elseOn loan

    Team lines, private worktree branches, candidate folders. Each has an owner, a recorded starting point, and a place it hands in to. When its work has been accepted or its owner is gone, it has expired.

What an Agent is told

Get a worktree. Update it. Hand it in.

That is the whole contract an Agent carries into a reviewed repository. Three verbs, each one command. Birth, retirement, ledgers and audits are Ronin's business and never appear in an Agent's brief beyond one line: hand in or close before you go.

  1. GetA private folder on a private branch, cut from the local working line. An Agent born into a Team gets one before its first prompt. Cutting from the working line, never from a team's queue, is what makes a stale starting point impossible.tejun-desk open
  2. UpdateMerge in what the working line has accepted since. The status line shows commits ahead and behind, so the Agent decides when to catch up. Nothing forces it and nothing blocks it.tejun-desk sync
  3. Hand inCommit, then hand the committed range to the team's line. Admission is mechanical and leaves a receipt. The Team lead reviews the line and promotes it to the working branch.tejun-desk hand-in

Who cleans up

The house tidies, and it tidies on its own schedule.

Ask an agent whether the tree is clean and it will look at its own folder, see no unsaved files, and say yes. It answered the question it could answer. The question you meant, whether anything exists that should not, needs a definition and a command, not a conversation. Ronin owns both.

  • At every promotion, the team's line is reset to the newly accepted working line, every private branch whose work is now accepted is deleted along with its folder and record, and the throwaway candidate folders go with them. A team line is never more than one promotion behind.
  • When a team closes, its line, its remaining worktrees and its records are cleared. Receipts stay: they are the history.
  • When a session ends, a worktree with no living owner is called out in red, with the three ways out: hand off, hand in, or close. The ending is never refused, only warned.
  • On a schedule, an audit checks that Ronin's records, Git's worktree list and the folders on disk agree; that every branch is accounted for; and that the working line is not quietly running ahead of the release. It reports on the Team board and exits non-zero when something is off.
  • Anything with work in it is never deleted quietly. A branch carrying commits the working line does not have is listed for you, with the commits, and removed only when you say so. Age and naming are never grounds for deletion.

Junk is expected. Sessions die mid-turn, folders get removed by hand, records go stale. The system is built to find that state and settle it, not to depend on nobody ever making it.

Tools, not a straitjacket

None of this corrals an Agent. The plain invocation of each tool is the clean path, so the stale base and the leftover branch are things the tools stop producing, not things a gate catches. Where a check remains, it tells and does not block: how far behind, which line is due for promotion, whose worktree has no owner. The Agent decides. Git commands stay Git commands. Nothing an Agent does pushes to your remote; publishing beyond the machine is a person's deliberate act. Read the no-behavioral-takeover promise.
