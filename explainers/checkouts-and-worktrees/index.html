Explainers / Checkouts and Worktrees

How should Agents work in this repository?

Two ways to work. Choose one per repository.

A repository is either a checkout, one folder everyone works in, or it uses Ronin Worktrees, a private folder per Agent with finished work patched back together through review. Choose once per repository. Both are first-class, and one Agent can hold both in different repositories.

The two models

Here are the two options, and this is what each looks like.

Use the checkout

One folder, one or more branches, everyone in it.

  • Work happens in the checkout. Commit on the branch as you go.
  • Ronin stays out. No hand-in, no lead, no records. Ordinary Git, run how you like.
  • Collisions are yours to avoid. A folder shows one branch at a time. Three Agents on three branches in one folder still collide: each switch swaps the files out from under the others.

Fits a workspace: notes, plans, a scratch repository, anything without a release.

Use Ronin Worktrees

A private folder per Agent. One choke point per team.

  • Work happens in a private folder on a private branch, cut from the working line.
  • The team is the choke point. Every worktree belongs to a team. Updates flow down from the working line freely; nothing flows back up except through the team's line and its lead's promotion.
  • Collisions cannot happen. A worktree is a branch with its own folder. Many Agents edit at once, and nobody's half-finished work reaches anyone else until it is accepted.

Fits a product: a codebase with a release, tests, and several Agents at once.

The difference is the folder, not the branch. Git gives you as many branches as you like, but one checkout shows one of them, so "just make your own branch" is still everyone sharing one set of files. A worktree gives a branch its own folder. That is what lets Agents work apart, and why their work has to be patched back together on purpose: the hand-in and the lead's look. A workspace needs neither.

Inside the worktrees model

Every team is a choke point. Many teams promote to one working line.

A worktree is cut from the working line and can pull its newest accepted work whenever it likes. It cannot put anything back. Its only way home is a hand-in to its team's line, and that line reaches the working line only when the Team lead promotes it. The line is the team's queue; the lead is its gate.

A team can be mid-flight for a week without touching anyone else's base. When its lead promotes, the working line takes the team's reviewed work as one step, and every other team sees it on its next update. Two leads promoting at once do not collide: the working line advances by compare-and-swap, and the second simply rebuilds on the first.

The branches

Two branches are the truth. Everything else is on loan.

A small file at the repository root names its working line and its stable line. Every tool reads that file; nothing is decided by whichever branch happens to be checked out.

  • local · working lineAccepted work

    Usually dev. Nobody edits it in place. Work reaches it by promotion, and every worktree is cut from it.

  • remote · stable lineReleased work

    Usually master or main on GitHub. It moves only by a pull request from the working line, which you review and merge yourself.

  • everything elseOn loan

    One line per team, a worktree branch per Agent, candidate folders. Each has an owner, a recorded starting point, and a place it hands in to. Once its work is accepted or its owner is gone, it has expired.

What an Agent is told

Get a worktree. Update it. Hand it in.

That is the whole contract, three verbs and three commands. Birth, retirement, ledgers and audits are Ronin's business and reach an Agent's brief as one line: hand in or close before you go.

  1. GetA private folder on a private branch, cut from the working line. An Agent born into a Team gets one before its first prompt. Cut from the working line, never from a team's queue, so a stale start is impossible.tejun-desk open
  2. UpdateMerge in what the working line has accepted since. Status shows ahead and behind; the Agent decides when. Nothing forces it and nothing blocks it.tejun-desk sync
  3. Hand inCommit, then hand the range to your team's line. Admission is mechanical and leaves a receipt. The Team lead reviews and promotes. That gate is the only way up.tejun-desk hand-in

Who cleans up

The house tidies, and it tidies on its own schedule.

Ask an agent whether the tree is clean and it looks at its own folder, sees no unsaved files, and says yes. The question you meant, whether anything exists that should not, needs a definition and a command. Ronin owns both.

  • At every promotion, the team's line is reset to the working line, every branch whose work is now accepted goes with its folder and record, and so do the candidate folders. A team line is never more than one promotion behind.
  • When a team closes, its line, its remaining worktrees and its records are cleared. Receipts stay: they are the history.
  • When a session ends, a worktree with no living owner is called out in red with the three ways out: hand off, hand in, or close. Never refused, only warned.
  • On a schedule, an audit checks that Ronin's records, Git's worktree list and the folders on disk agree, that every branch is accounted for, and that the working line is not quietly running ahead of the release. It reports on the Team board.
  • Anything with work in it is never deleted quietly. A branch carrying commits the working line lacks is listed for you, with the commits, and removed only when you say so.

Junk is expected. Sessions die mid-turn, folders get removed by hand, records go stale. The system finds that state and settles it rather than depending on nobody making it.

Tools, not a straitjacket

None of this corrals an Agent. The plain invocation of each tool is the clean path, so the stale base and the leftover branch are things the tools stop producing, not things a gate catches. Where a check remains it tells and does not block. Git commands stay Git commands, and nothing an Agent does pushes to your remote. Read the no-behavioral-takeover promise.
