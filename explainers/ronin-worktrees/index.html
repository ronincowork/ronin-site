Explainers / Ronin Worktrees

How do several Agents share one repository without stepping on each other?

Each Agent in its own worktree. One reviewed path back.

Ronin Worktrees gives a coding Agent a private working folder and branch inside your repository. Agents work in parallel without file collisions, and finished work returns through a hand-in the Team lead reviews — never by landing directly on the shared branch.

The whole idea in three keys

What it does, when it works, what it costs.

  • What it doesIsolated working folders and branches keep parallel Agents from colliding in the same files. Two Agents can edit the same repository at once; neither sees the other's half-finished state.
  • When it worksBoth sides must say yes. The repository's Project Root enables Worktrees — one tick in its editor — and the Agent carries the Worktrees Routine. Either side off means the Agent simply uses the ordinary checkout and ordinary Git.
  • The tradeoffWork leaves a private worktree through the managed path: commit, hand-in, and the Team lead's merge. That is a review step between an Agent and your shared branch — deliberate friction, and the point.

Setup is two ticks

The repository opts in. The Agent opts in. That's it.

  • The repository sideIn the Project Root editor, the Worktrees setting offers two answers: Use Ronin Worktrees or Use the checkout. Tick the first and the repository accepts managed worktrees from capable Agents. Nothing moves when you save — the setting shapes future launches, not running work.
  • The Agent sideThe Worktrees Routine travels the ordinary defaults path: the Campaign sets a default, a Team may override it, and the New Agent form shows the resolved answer for each launch. An Agent born with it on knows the workflow from its first breath — the Routine hands the working method over at birth, so you never have to teach it.
  • Per repository, not all-or-nothingThe answer resolves separately for every repository in an assignment. One Agent can hold a managed worktree in the repository that wants review and an ordinary checkout in the one that doesn't.

The working loop

Commit preserves. Hand-in shares. The lead's merge publishes.

A private worktree at birth
The Agent starts on its own branch, in its own folder, inside your repository.

The Agent's half

  1. Commit — preserves work on the private branch. Private means private: nothing reaches anyone else yet.
  2. Hand in — publishes the committed work to the team's shared line. Admission is mechanical; a receipt records exactly what arrived and from whom.

The Team lead's half

  1. Review the line — the lead reads the assembled candidate: every hand-in, with its receipts, as one coherent state.
  2. Promote — the full verification runs once, on the exact candidate. Only a passing candidate advances the shared branch, and the receipt proves which commit passed.Publishing beyond the machine — a push, a release — remains a person's deliberate act.
The shared branch advances
Everyone's next worktree grows from the accepted state, and the loop begins again.

Every step leaves a receipt, so a failure is attributable: the lead can see which hand-in broke the candidate and send it back, without unwinding anyone else's work.

Coordination, not confinement

Worktrees prevent accidental collisions; they are not a security boundary, and Use the checkout remains a complete, first-class way to work — many repositories never need review machinery. An Agent's authority on the machine is governed by the machine, not by which folder it works in. Read the no-behavioral-takeover promise.
